# План тестирования Ozen-Sync

Три сценария из ТЗ. Для каждого: проверка в 1С (ручная, на тестовой базе с установленным
расширением) и автоматическая/полуавтоматическая проверка без 1С.

Подготовка:

```bash
cd emulator
python -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt     # Linux/macOS: .venv/bin/pip
.venv/Scripts/python -m uvicorn app.main:app --port 8000
```

## Тест 1 — Outbox: проведение создаёт запись с валидным JSON и не блокирует пользователя

**Что проверяем.** Подписка `ПриЗаписи` пишет сообщение в той же транзакции, что и документ;
при проведении нет сетевых вызовов.

### В 1С

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | **Остановить** эмулятор. Провести документ продажи абонемента. | Документ проводится так же быстро, как без расширения (нет ожидания таймаута 15 сек). |
| 2 | Открыть *РС «Очередь обмена с бухгалтерией»*. | Одна новая запись: `Статус = Ожидает`, `КоличествоПопыток = 0`, `ТипОбъекта = ПродажаАбонемента`, `Операция = upsert`, `ОбъектСсылка` = документ. |
| 3 | Скопировать `ТелоJSON` в файл `msg.json` и проверить его эмулятором (запустить снова): `curl -X POST localhost:8000/api/v1/accounting/validate -H "Content-Type: application/json" --data-binary @msg.json` | `200 {"status":"valid", ...}` — JSON синтаксически корректен и соответствует контракту. |
| 4 | Перепровести документ без изменений. | Вторая запись с бо́льшей `Версия` (полный снимок; приёмник сделает upsert). |
| 5 | Отменить проведение документа. | Запись с `Операция = cancel`. Повторная запись непроведённого документа новых сообщений **не** создаёт. |
| 6 | Записать черновик нового документа (без проведения). | Записей в очереди нет. |
| 7 | **Атомарность.** На тестовой базе вызвать `ВызватьИсключение` в обработке проведения после записи (или провести документ, который не проходит контроль остатков). | Документ не проведён **и** записи в очереди нет — транзакция откатилась целиком. |
| 8 | Провести документ пользователем без прав на регистр очереди. | Проведение успешно (подписка работает в привилегированном режиме). |

## Тест 2 — Resilience: падение сервиса не роняет 1С, данные досылаются

**Что проверяем.** Ошибки сети/5xx не поднимаются наружу, копятся счётчик и текст ошибки,
работает экспоненциальный бэкофф, после восстановления всё досылается ровно один раз.

### В 1С

Для скорости на время теста поставить в `ozs_ОбменСБухгалтериейНастройки.Параметры()`
`БазоваяЗадержкаСек = 5`, `МаксимальнаяЗадержкаСек = 60`.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Остановить эмулятор. Провести 5 документов. | 5 записей `Ожидает`. |
| 2 | *Администрирование → Регламентные и фоновые задания → «Ozen-Sync: отправка» → Выполнить сейчас* (или в консоли кода: `ozs_ОтправкаВБухгалтерию.ОбработатьПачку()`). | Задание завершилось **без ошибки**. У первого сообщения `КоличествоПопыток = 1`, `ТекстОшибки = "Сервис недоступен: …"`, `ДатаСледующейПопытки` ≈ сейчас + 5–6 сек. Остальные 4 не тронуты (circuit breaker — не ждём таймаут 5 раз). В ЖР — предупреждение `Ozen-Sync.Отправка … сервис недоступен`. |
| 3 | Подождать несколько запусков задания (или вызывать вручную). | Счётчики попыток растут, задержки удваиваются: 5 → 10 → 20 → 40 → 60 сек (+ джиттер до 20%). Статус остаётся `Ожидает` при любом числе сетевых ошибок. |
| 4 | Запустить эмулятор с `OZEN_FAILURE_RATE=0.2`. | — |
| 5 | Дождаться 2–3 запусков задания. | Все 5 записей `Отправлено`, `КодОтвета = 200`. Часть сообщений имеет `КоличествоПопыток` > 1 из-за искусственных 500. |
| 6 | `curl localhost:8000/api/v1/accounting/documents` | Ровно 5 документов, у каждого `deliveries = 1`. `GET /api/v1/admin/stats` → `simulated_failures` > 0. |
| 7 | `curl -X PUT localhost:8000/api/v1/admin/chaos -H "Content-Type: application/json" -d "{\"failure_rate\": 1.0}"`, провести документ, дождаться `МаксимумПопыток` запусков. | Сообщение уходит в `Ошибка` (dead letter) с текстом последнего ответа 500. |
| 8 | Вернуть `failure_rate` в 0, выполнить `ozs_ОтправкаВБухгалтерию.ПереотправитьОшибочные()`. | Сообщение снова `Ожидает` с обнулённым счётчиком и при следующем запуске — `Отправлено`. |

### Без 1С: симулятор очереди

[`tools/outbox_simulator.py`](../tools/outbox_simulator.py) — построчный порт логики
`ozs_ОтправкаВБухгалтерию` на Python + SQLite (только стандартная библиотека).

```bash
python tools/outbox_simulator.py reset
python tools/outbox_simulator.py enqueue --count 10 --invalid 1
```

```bash
python tools/outbox_simulator.py run --once
```

```bash
python tools/outbox_simulator.py table
```

Запустите `run --once` несколько раз при **выключенном** эмуляторе, затем включите эмулятор
и выполните:

```bash
python tools/outbox_simulator.py run --until-empty --interval 1
```

Фактический прогон (эмулятор с `OZEN_FAILURE_RATE=0.2`, `OZEN_SEED=7`):

## Тест 3 — API contract: эмулятор отсекает некорректные пакеты

```bash
cd emulator
.venv/Scripts/python -m pytest -v
```

Покрыто в [`emulator/tests/test_api.py`](../emulator/tests/test_api.py) (32 теста):

| Группа | Что проверяется |
|---|---|
| Обязательные поля | Отсутствие любого из `document_id`, `client_name`, `amount`, `items`, `object_type` → `400` с указанием поля |
| Типы и значения | Невалидный UUID, пустое/пробельное имя, `amount` ≤ 0 или строкой, пустой или не-массив `items`, неизвестный `object_type`/`operation`/`currency`, строки `items` без `name`, с `quantity = 0`, `price < 0` |
| Бизнес-правило | `amount` ≠ сумме строк → `400` |
| Синтаксис | Обрезанный JSON → `400` |
| Побочные эффекты | Отклонённый пакет не сохраняется; `/validate` ничего не сохраняет |
| Порядок | Валидация выполняется до хаоса: при `failure_rate = 1.0` битый пакет всё равно `400` |
| Гарантии | Дедупликация по `Idempotency-Key`; новая версия обновляет запись; старая версия игнорируется; `cancel` |
| Хаос | `failure_rate = 1.0` → всегда `500`; при `0.2` на 500 запросах доля сбоев 15–25% |

Ручная проверка:

```bash
curl -i -X POST localhost:8000/api/v1/accounting/sync -H "Content-Type: application/json" -H "Idempotency-Key: test-1" --data-binary @docs/payload-example.json
```

```bash
curl -i -X POST localhost:8000/api/v1/accounting/sync -H "Content-Type: application/json" -d "{\"document_id\": \"123\", \"items\": []}"
```

Второй запрос возвращает `400` со списком всех нарушений сразу:
`document_id` (не UUID), `client_name`, `amount`, `object_type` (отсутствуют), `items` (пустой).
